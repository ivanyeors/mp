## The pillow half of the shopper x-ray never returns a Filling Template

**Where:** `lib/shop/customization-llm.ts` → `getBomTemplates(kind, size)`
**Callers:** `app/api/shop/customize/route.ts` (pillow branch),
`app/api/mp-basic/recommend/route.ts`
**Status:** open, pre-existing (predates ADR 0018), owner: Ivan

`getBomTemplates` filters `.eq("kind", "pillow").eq("key", size).eq("pillow_kind", kind)`
with `kind ∈ {basic, premium}`. A **Filling Template** always has
`pillow_kind = null` — set explicitly at
`app/[lang]/settings/inventory/configure/templates/route.ts` and
`configure/unpromoted/route.ts`, because Filling Templates carry no **Tier**
(CONTEXT.md). So that predicate can never match one, and the query returns
**warehouse** templates instead.

Both callers then read `filling_template_placements` for the returned ids, to
render the recommended mix in the shopper's read-only x-ray. Placements exist
only for `role = 'filling'` rows (`20260724000000_backfill_filling_placements.sql`),
so the join returns nothing and the pillow x-ray renders empty.

Two readings, unresolved:

1. **Dead code.** The pillow x-ray was never wired up, and the `pillow_kind`
   filter is a leftover from when this read warehouse BOMs.
2. **A real bug.** It is meant to read Filling Templates, in which case it also
   needs the ADR 0018 treatment — scope by **Size membership**
   (`templateIdsForKey`), not by `key`, or a recipe shared across sizes shows on
   its primary size only.

The bolster half of the same endpoint (`app/api/shop/customize/route.ts`, the
`role = 'filling'` query) does exactly what reading (2) describes, which makes
(2) the more likely intent — but the pillow branch has no equivalent, so this is
a product call, not a mechanical fix.

**If you fix it:** drop `.eq("pillow_kind", kind)`, add `.eq("role", "filling")`,
and scope by membership via `templateIdsForKey` from
`lib/filling-templates/membership.ts`. Add the call site to the reader list in
`lib/filling-templates/membership.check.ts` so it cannot regress.

## A price change that fails to reach Stripe is still reported as saved

**Where:** `lib/shop/price-sync.ts` → `syncVariantPricesFromCostings` (it returns
`stripeSync`, which no caller reads)
**Callers:** `app/[lang]/settings/costings/save/route.ts`,
`app/api/shop/products/resync-prices/route.ts`, and the `.catch(() => {})` calls in
`lib/ecommerce/from-inventory.ts`, `shop-listings.ts` and `inventory-sync.ts`
**Status:** open, pre-existing, found 2026-11-21 by the second check on the Stripe sync
fix, by reading. Awaiting the owner's decision

Checkout charges a line by the Stripe Price id stored on its Variant
(`lib/stripe/checkout.ts`), but totals the Order from `product_variants.price`
(`app/api/shop/checkout/route.ts`). A Costings save writes the new price to the Variant
and then syncs it to Stripe. If that sync fails (Stripe unreachable or rate limited),
the Variant keeps its old Price id, still active at the old amount, and:

- the save answers `ok`, and the reason goes to `console.error` only. The product
  editor's own saves do warn ("Saved, but couldn't sync to Stripe");
- until a sync succeeds, a customer buying that Variant is charged the old amount, the
  `checkout.session.completed` webhook records `total_mismatch`
  (`app/api/stripe/webhook/route.ts`) and the paid Order is not confirmed.

The sync's notice that an old Price is still active in Stripe is lost on this path the
same way.

**If you fix it:** carry the failure out of `syncAllAutoGeneratedProductPrices` (the
product and Stripe's message) and return it from both routes beside
`unresolvable_variants`, shown as a warning that names the product and points at *Sync
to Stripe*. Test that the Costings save response carries it when
`syncProductToStripeSafe` answers `synced: false`.

## A product's payment link is one column for both Stripe modes, and a price change does not refresh it

**Where:** `lib/stripe/sync.ts` → `createPaymentLink`; `products.stripe_payment_link`
and `stripe_payment_link_id`
**Status:** open, pre-existing, found 2026-11-21 by the second check on the Stripe sync
fix, by reading; not reproduced against Stripe. Awaiting the owner's decision

Localhost runs on the Stripe sandbox and Vercel on live, against one database
(`supabase/migrations/20260913120000_stripe_ids_per_mode.sql`). Product and Price ids
got a `_test` column each; the payment link did not.

1. **Generated from the other mode.** Deactivating the stored link answers
   `resource_missing`, because it belongs to the other account, and that is stepped
   over. The new link overwrites the row: the other mode's link stays live with no row
   pointing at it, and the editor on the live site shows a sandbox link (or the
   reverse).
2. **After a price change.** A link is bound to the default Variant's Price id when it
   is made. The sync archives that Price and makes a new one, and nothing regenerates
   the link. What an existing link does once its Price is archived was not checked
   against Stripe; if the archive failed, the link keeps selling at the old amount.

**If you fix it:** give the link per-mode columns like the ids (a migration the owner
applies; `lib/stripe/mode.ts` picks between them), and when the sync replaces the
default Variant's Price, deactivate the link and say so.

## A return (RMA) refund is worked from the unit price before any discount

**Where:** `lib/rma/refund.ts` → `rmaRefundAmount`
**Callers:** `app/[lang]/settings/rma/actions.ts` (the refund on a received return)
**Status:** open, pre-existing, found 2026-11-21 by the second check on the refund fix,
by reading. A product call, awaiting the owner's decision

It refunds `order_items.unit_price × quantity` for the returned lines, capped at the
Order's refundable balance. `unit_price` is the price before the Order's discount. A
staff refund of the same line (ADR 0038, `lineRefundAmount`) refunds its share of what
was paid. Two S$100.00 lines with 20% off paid S$160.00: a return of one line refunds
S$100.00, and *Choose items* on the same line refunds S$80.00.
`lib/rma/__tests__/rma.property.test.ts` ("a return's refund is exactly its lines at
their unit price, to the cent") pins the current rule.

Two readings, unresolved:

1. **Intended.** A return gives back the line's unit price, whatever discount the Order
   had.
2. **A defect.** It should give back what the customer paid for those lines.

**If you fix it:** work the amount with `lineRefundAmount` over the Order's lines, and
change the property to match.
